Latest release 0.0.19 · GPL-3.0

A supervisor for long-running programs, each in its own sandbox.

Pythonator runs bots, web servers, workers and scheduled jobs, restarts them when they fail, and confines each one to its own folder and the ports it declares. It includes a code editor, and plugins add alerts, policy rules and project templates. It runs on Windows, macOS and Linux.

Download Getting started

From source with Python 3.12 or later: pip install -e ., then pythonator. Needs no Docker, WSL or administrator rights.

01 · Supervision

Supervised, and kept running.

A service is a file to run or a command. A background process runs it, independently of the window, and applies the service's restart rule after every exit.

Restarts that back off

On failure or always, with the delay doubling from 1 s to 60 s. After too many restarts in ten minutes it stops and reports the failure rather than looping indefinitely.

Restarts

Schedules and limits

Presets, a form, every 15m or any cron expression. Memory and CPU limits for the whole process tree, enforced by a job object on Windows, the engine in containers, and a watchdog elsewhere.

Schedules · Limits

A console that keeps up

ANSI colours, standard input or a shell, and floods of output without freezing the window. Secret values from the environment are masked before anything is displayed or logged.

Console and logs

Code from Git

Clone a repository as a service and optionally pull before each start: fast-forward only, hooks and submodules disabled, https and ssh only.

Git

An editor beside it

Built on QScintilla (the Scintilla engine used by Notepad++): highlighting for every supported language, folding, multiple carets, find and replace, and large files without lag.

Shortcuts

Packages stay with the project

Each service gets its own .venv, node_modules, vendor or package cache, installed inside the service's isolation. Nothing is installed globally.

02 · Isolation

Three modes, with Sandbox as the default.

The sandbox uses the containment each operating system already provides. If a protection cannot be applied, the service does not start; it never falls back to running with less.

ModeWhat it can reachBuilt on
SandboxIts own folder, its runtime, and the listed ports. Not the home folder, keys, other projects or Pythonator's data.Landlock, seccomp and bubblewrap on Linux, Seatbelt on macOS, AppContainer on Windows
ContainerOnly the project folder, mounted at /app. Can join a container network to reach a database.Docker or Podman with every capability dropped, a read-only image and no new privileges

03 · Ports and APIs

Only the declared ports, for the chosen audience

Each service lists the ports it serves, and in Sandbox mode may listen on those alone. This computer only suits a local API; Other computers too opens it to the local network. On Windows, Make reachable adds the loopback exemption and firewall rules for that one service in a single administrator prompt, and Undo removes them.

04 · Plugins

Official plugins are verified; others are contained.

Plugins run as separate processes in the same sandbox as services, and talk to Pythonator only through a small, validated message protocol. A plugin is official only if its files match a reviewed SHA-256 catalogue. Any other plugin starts in test mode with no permissions, and its actions are only recorded until permissions are granted.

  • Notify: one timeline of crashes, blocked starts, recoveries, failing health checks and anomalies, sent to Discord, Slack, Telegram, Teams, ntfy or any URL
  • Guard: rules for modes and ports before a start, and a watchdog for memory and CPU
  • Project builder: 38 templates (React, Next.js, FastAPI, Django, Go, Rust, bots and more), each created by the framework's own tool, in a sandbox
  • AI assistant: questions about a service's logs and code, with suggested changes that are reviewed before anything is written

05 · Install

From a release or from source

Installers for Windows, macOS and Linux are on the releases page. Installing from source needs Python 3.12 or later; the six dependencies are pinned with hashes in requirements.lock and audited for known vulnerabilities on every change.
